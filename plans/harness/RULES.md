# Правила выполнения

## Авторизация и область

1. Следовать текущему прямому указанию пользователя. На этапе подготовки изменяются только документация/harness и новая локальная ветка. После указания реализовать — scope плана 002.
2. Не менять main/default branch, remote/backend configuration и gh-pages. Commit/push/deploy — только отдельное указание; не считать разрешение создать ветку разрешением публикации.
3. Не трогать посторонние untracked-файлы из baseline. Не выполнять массовое форматирование, перенос repo или переписывание контента.
4. Агентов не запускать автоматически; явная делегация нужна только при отдельном запросе или применимой инструкции.

## Рабочий цикл

1. Проверить ветку/status и прочитать tasks.json, актуальный план, последние записи ERRORS.
2. Выбрать один этап с выполненными зависимостями. Записать ожидаемый observable outcome и scope до правки.
3. Структурный перенос сначала проверить без изменения поведения. Затем менять поведение ограниченными порциями.
4. Выполнить проверки этапа. Сохранить команду, cwd, exit code, фактический результат и ограничение в RUN_LOG.
5. При проблеме зарегистрировать ERR-ID. Отделять наблюдение от гипотезы причины. После исправления повторить именно упавшую проверку.
6. DONE только при успешных обязательных gate и наличии evidence. Любая NOT_RUN-проверка, обязательная для этапа, исключает DONE.
7. Зафиксировать следующий шаг и остаточный риск. Не повторять зелёные проверки без новой причины.

## Инварианты игры

- Нет вызовов игрового API в lite, включая bootstrap, direct fetch, event logging, telemetry, retry/polling.
- Full access не меняет passes, scores, completedScripts или XP. Dev-admin не служит доступом к чтению.
- Весь контент берётся из действующих frontend-реестров; черновики и личные server-данные не публикуются.
- Сохранение только lite-snapshot; старые guest/account keys не читаются для auth и не изменяются.
- Честные заглушки: нет фиктивной отправки, AI-ответа, синхронизации и расхода валюты.
- Build/typecheck не заменяют browser/network tests. Прерывание запроса тестом не означает отсутствие попытки запроса.

## Работа с ошибками и улучшение процесса

После ошибки: наблюдение → воспроизведение → минимальное исправление → проверка результата → конкретная профилактика. Гипотезу причины не превращать в факт без проверки. Категории: environment / git / implementation / test / process. Если причина повторяется дважды после разумного исправления, остановить зависимый этап и пересмотреть гипотезу; независимую работу продолжить.

Новые правила добавлять только когда есть ERR-ID, механизм повторения и проверяемое снижение риска. В ERRORS указать RULE/DEC-ID изменения и подтверждение. Глобальные запреты из единичного случая не выводить. Удалять/сужать правило при наличии опровергающего свидетельства с записью причины.

В журналах нет паролей, JWT, .env, персональных дневников и raw request bodies. Использовать синтетические fixtures. Старые ошибочные выводы не стирать: пометить опровергнутыми новой записью.

## Windows и инструменты

- Явно задавать cwd: настоящий Git-root вложен в исходный workspace.
- Для npm использовать npm.cmd; проверять exit code каждой существенной команды.
- rg glob задавать через -g, например rg -n 'pattern' src/components/JourneyView -g '*SkillTree.tsx', а не Windows-путём с wildcard.
- Команды Git merge-base и rg могут возвращать exit 1 как содержательный результат; фиксировать его отдельно.
- Стандартный exec в этой сессии ранее падал на apply deny-read ACLs. Если повторяется, не маскировать вывод: использовать штатный escalation с узкой причиной. Это workaround среды, не разрешение обходить реальный отказ авто-проверки.
- Для текстов PowerShell использовать literal here-string или файл; JSON.stringify не является shell quoting.
- Не удалять каталоги ради исправления инструмента. Перед новым браузерным сервером проверить listener, PID и HTTP; strictPort исключает незаметную смену порта.

Большие документы записывать отдельными ограниченными командами, не одним общим here-string пакетом: ERR-006 показала лимит Windows command line.
